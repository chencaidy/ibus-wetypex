# 从 Fcitx5 迁移到 IBus：可行性与实施建议

## 结论

**技术上可行，但不是把 Fcitx5 插件改几个 API 名称就能完成的迁移。** WeTypeX 的原版输入核心、引擎宿主、私有 JSON IPC、账户与同步服务主要位于输入法框架之外，可以继续复用；真正需要重做的是 Linux 输入法前端以及与它绑定的配置、安装、发行和测试集成。

| 维度 | 评估 |
| --- | --- |
| 核心与业务逻辑复用 | 高：后端通过私有 JSON 管道接收按键/操作并返回候选、预编辑和提交，不需要直接依赖 Fcitx 类型 |
| 输入法前端改造 | 高：按键状态机、每个输入上下文的状态、候选呈现和若干 Fcitx 专属能力都集中在插件中，但需适配 IBus 生命周期和客户端差异 |
| 设置与配置兼容 | 中：设置窗口、JSON 配置和大部分业务设置可保留；Fcitx 配置页、快捷键类型、配置目录需要替代或迁移 |
| 打包与维护 | 中到高：CMake、依赖、安装路径、各发行版元数据、CI 和用户文档目前都以 Fcitx5 为中心 |
| 建议 | **先增加 IBus 前端并保留 Fcitx5 前端**；完成端到端验证后，再决定是否停止发布 Fcitx5 版本 |

这是一项输入法集成层的实质性移植，不是对原版核心的重写。若目标是扩大桌面环境支持，双前端路线比直接替换更稳妥，也可以共用现有用户运行时和业务数据。

## 当前结构与可复用边界

当前输入路径可概括为：

```text
应用
  │ Fcitx5 InputContext / 按键事件
  ▼
src/plugin/wetype.cpp
  │ 私有 JSON 行协议
  ▼
wetypex-backend → wetypex-engine-host → 原版输入核心
```

### 可以继续复用

- `wetypex-engine-host`、原版核心与词典的加载和 ABI 兼容代码。
- 插件与后端之间的 JSON 操作协议、会话 ID、序号、epoch、候选修订号及异步更新机制。IBus 前端可实现相同协议，后端不必认识 Fcitx5 或 IBus。
- 账户配对、设备同步、词库、语音、AI、文件传输和安装运行时的主要业务程序。
- IBus 设置窗口使用独立的 `src/ibus-settings` GTK4 + libadwaita 实现，只读写 IBus 实际使用的配置项；Fcitx5 的 Qt 设置窗口保持不变。
- 桌面剪贴板、音频采集和网络桥接工具，只要新前端继续提供相同的操作及焦点语义。

`src/ai/main.cpp` 是独立 Qt 窗口，不是 Fcitx5 插件；可以保留。迁移时仍需检查窗口应用标识、资源目录和 helper 命令等含 `fcitx5` 的路径/名称。

### 必须重做或重新接线

核心实现集中在 [`src/plugin/wetype.cpp`](../src/plugin/wetype.cpp)，该文件直接使用 Fcitx5 的 `InputMethodEngine`、`InputContext`、`KeyEvent`、`InputPanel`、`CommonCandidateList`、状态区操作、事件循环和配置 API。IBus 不能直接加载这个插件。

新 IBus 前端至少要覆盖：

1. **输入上下文生命周期**：创建、启用、焦点进入/离开、重置、销毁和密码上下文处理，并为每个上下文保存独立会话状态。
2. **按键和修饰键**：按下/释放事件、键值规范化（包括小键盘数字）、Shift 单键切换、可配置快捷键、候选选择/翻页，以及将未处理按键交还应用。需要重点验证 IBus 对 release、修饰键和不同客户端的事件行为。
3. **预编辑与提交**：内嵌预编辑、光标位置/属性、辅助提示、提交和输入焦点变化时的清理。要对照 IBus API 与各目标客户端的实际支持，不能假设所有客户端的呈现一致。
4. **候选列表**：将后端候选、页码、高亮、选择和异步刷新映射到 IBus lookup table；维持现有修订号校验和“输入后立即空格/数字选词”的顺序保证。
5. **周边文本和光标行为**：AI 上下文、数字/标点修正、自动符号配对及光标移动目前会使用 Fcitx5 的 surrounding text、光标提交或按键转发能力。对 IBus 的能力和各客户端差异需要先做原型验证；不能可靠等价的行为应降级或暂缓，而非悄悄改变。
6. **特殊 UI 与扩展**：V 模式候选菜单、输入法状态区设置入口、剪贴板历史集成、候选主题/外观行为需要寻找 IBus 对应实现，或由项目自有窗口和系统剪贴板接口承接。
7. **配置入口**：`src/configui/main.cpp` 是 Fcitx5 Qt 配置插件，`src/plugin/config.hpp` 使用 Fcitx 配置类型；两者都不能原样作为 IBus 配置页。可先让独立设置程序继续编辑 JSON，再逐步提供 IBus 原生设置入口。

## 关键迁移风险

### 1. 输入行为和异步顺序

现有前端不仅把按键发给后端，还负责丢弃失焦/过期回复、保护候选修订、排队处理快速输入与选词、处理迟到更新，以及在重置时递增 epoch。迁移若只实现“按键转发 + 展示候选”，容易出现串字、重复提交、焦点切换后旧候选复现等回归。

**要求：** 保持 JSON 协议及序号/修订语义；在 IBus 前端实现等价的上下文状态和取消规则。不要把输入顺序和上下文状态迁移到全局共享对象。

### 2. 客户端、桌面与显示协议差异

预编辑、候选框、按键释放、周边文本和焦点恢复取决于 IBus、桌面 Shell、Wayland/X11 以及应用输入工具包的组合。现有项目主要在 Arch、KDE Plasma、Wayland 上验证，不能据此推断 GNOME、X11、GTK、Qt、浏览器或终端客户端都具备相同能力。

**要求：** 建立真实客户端矩阵；标注能力检测和降级行为。特别检查密码框旁路、候选窗口关闭、V 模式选择后焦点返回、AI 周边文本以及符号自动补全。

### 3. 配置和用户数据

当前配置默认在 `~/.config/fcitx5/wetypex.json`，部分工具也直接读取该路径；运行时和业务数据则使用 `fcitx5-wetypex` 名称。直接改目录会造成现有配置、账户身份和用户词库看起来“丢失”。

**建议：** 把配置和用户数据目录保持为兼容位置，或实现明确的旧路径读取/迁移流程。运行时数据（账户、同步状态、运行时核心）默认不迁移、不重建。双前端运行时，两者必须共用配置时要明确文件并发写入和热加载策略。

### 4. 发行版和升级路径

[`CMakeLists.txt`](../CMakeLists.txt) 直接查找 Fcitx5、Fcitx5 配置组件、剪贴板模块和 Fcitx5 Qt Addons，并把插件与输入法描述文件安装到 Fcitx5 目录。Arch、Debian/RPM、Ubuntu 20.04 SDK 构建和 GitHub Actions 也分别声明了 Fcitx5 依赖、插件路径或输出包名。

迁移会涉及至少以下工作面：

- CMake 依赖发现、目标与安装规则；新增 IBus 开发依赖和 IBus component/engine 安装元数据。
- 包依赖、包名/描述、卸载与升级行为、运行时命令和首次设置提示。
- Ubuntu 旧系统构建镜像、发行流水线和包产物检查。
- README、安装说明、配置/故障排查文档和桌面输入法添加说明。

只替换 C++ 插件而不改这些入口，无法得到可安装、可发现或可升级的 IBus 输入法。

## 推荐方案

### 方案 A：并行支持 Fcitx5 与 IBus（推荐）

新增独立 IBus 引擎前端，继续保留现有 Fcitx5 插件和包。两个前端只通过稳定的 JSON 协议访问同一个后端，不共享框架对象。先以单独包或可选构建目标发布 IBus 变体，验证真实桌面矩阵后，再考虑统一包。

**优点：** 回滚容易；复用当前稳定实现；能对比两套前端行为；用户可以自行选择。  
**代价：** 短期需要维护两套框架适配、配置入口和包测试。

## 方案 A 落地状态

已按方案 A 开始实现：Fcitx5 仍为默认构建前端；IBus 使用独立引擎和单独的 `ibus-wetypex` Debian 包，不要求安装 Fcitx5。CMake 可通过 `WETYPE_BUILD_FCITX5` 与 `WETYPE_BUILD_IBUS` 分别选择前端。Ubuntu 26.04 的独立包构建入口为 `packaging/build-ubuntu-package.sh`。

IBus 首版范围为全拼、双拼、五笔、预编辑/候选交互，以及沿用现有用户配置和远程剪贴板同步。AI、语音、V 模式和剪贴板历史不由此版 IBus 前端提供。后端和已有业务工具仍共享项目现有路径与数据；两个前端不应同时编辑同一份配置。

当前前端及独立包属于初始移植实现，尚未完成 Ubuntu 26.04 / GNOME 50 / Wayland 的端到端桌面验证。C++ 语法检查不代表 IBus 注册、候选交互、剪贴板同步或包安装已经验收。发布前应执行本文件的阶段验收与回归矩阵，并据实际测试结果更新功能状态。

### 方案 B：直接替换 Fcitx5

停止构建和发布 Fcitx5 插件，将包、文档、依赖与安装流程整体切换到 IBus。

**优点：** 最终维护一个前端。  
**代价：** 迁移期间没有现成输入法回退；所有功能和发行版必须一次完成适配；需要处理现有安装和桌面用户配置迁移。

除非已经决定停止支持 Fcitx5，且有覆盖目标桌面的 IBus 测试资源，否则不建议一开始采用方案 B。

## 建议实施阶段与验收标准

### 阶段 0：IBus API 原型与能力清单

- 明确最低 IBus 版本、桌面发行版和客户端范围。
- 做最小引擎原型：注册引擎、接收按键、显示预编辑/候选、选择并提交文本。
- 实测 key release、surrounding text、候选方向/分页、焦点和 Wayland/X11 行为。

**验收：** 在至少一个 GTK 应用和一个 Qt 应用中完成拼音输入、候选选择、取消、切换窗口和密码框测试；列明未支持能力及降级策略。若原型暴露出候选/按键语义无法满足核心交互，先调整范围，再开始完整移植。

### 阶段 1：并行 IBus 适配层

- 新增独立 IBus 引擎模块，将 IBus 事件转换为当前 JSON 协议。
- 移植每上下文状态、会话/序号校验、异步候选更新、候选修订选择、重置和失焦清理。
- 第一批覆盖全拼、双拼、五笔、预编辑、提交、数字/空格选词和密码上下文旁路。

**验收：** 后端不需要针对 IBus 分支；两套前端都能连接同一运行时；快速输入、候选异步刷新和重复焦点切换没有丢字、重复提交或过期 UI。

### 阶段 2：功能对齐与降级策略

- 逐项迁移快捷键、状态显示、候选外观、标点/符号、AI、V 模式、语音、微信表情和剪贴板入口。
- 为 IBus 不提供或客户端不支持的能力定义显式 fallback；不可安全降级的能力先不开放。
- 共享同一配置文件，并验证 Fcitx5 与 IBus 两种前端读取既有 JSON 的兼容性。

**验收：** 更新功能状态表，按能力逐项给出支持、降级或暂不支持状态；所有支持项都有目标客户端测试记录。

### 阶段 3：打包与发布

- 增加 IBus 运行时/开发包依赖、引擎元数据、安装位置和包完整性检查。
- 更新 Arch、Debian/RPM 与旧版 Ubuntu 构建，以及 GitHub Actions 发布产物。
- 决定采用单包双引擎还是独立 IBus 包，明确与现有 Fcitx5 包的冲突关系和升级方式。

**验收：** 从干净系统安装、发现并启用引擎；升级不覆盖/删除用户数据；卸载行为符合包管理器约定；发布包测试能发现 IBus 引擎及其元数据。

## 已确认的项目决策

1. **前端策略：** 增加 IBus，保留 Fcitx5。
2. **首发环境：** Ubuntu 26.04、GNOME 50、Wayland、发行版提供的 IBus 1.5.34。
3. **首版功能：** 暂不覆盖 AI、语音、V 模式和剪贴板历史；保留跨设备远程剪贴板同步。
4. **发行方式：** 使用 `ibus-wetypex` 包名，独立于 Fcitx5 包发布；继续兼容现有配置和数据路径。
5. **符号自动配对：** IBus 协议没有“带光标位置的提交”，唯一可用的 `ForwardKeyEvent` 在 GTK4 与 Qt 客户端中被丢弃（GTK4 将其重投回 IBus IM context 后作废），因此 IBus 前端不补右半边：括号只提交左半边，引号左右交替；`symbol_auto_pair` 对 IBus 前端不生效，Fcitx5 前端行为不变。
6. **修饰键透传：** IBus 前端不消费 Shift 的按下和释放（单键切换只在“无其他按键、且两侧 Shift 都已松开”时于释放事件里触发）。客户端依赖收到的按键序列维护修饰状态，吞掉 Shift 会让 Shift+点击无法选中文本；同理，待选词缓冲期间也不缓冲修饰键。单键切换的判定直接对齐 librime `ascii_composer`：按下到松开不超过 500 ms、期间没有其他实体按键、也没有 Ctrl/Alt/Super 等组合参与；不做周边文本/光标探测等额外兼容。
7. **自动符号转换（`symbol_auto_change`）：** IBus 前端不实现。该功能需要把已提交的“全角标点+数字”替换为半角形式，依赖 `DeleteSurroundingText`；Qt 的 IBus 客户端会把替换退化成追加（`12:0` → `12:0:0`），且按客户端分流的兼容成本过高，因此整体从 IBus 前端移除，`symbol_auto_change` 对 IBus 前端不生效，Fcitx5 前端行为不变。
8. **中英状态属性：** 面板只通过 `RegisterProperties` 信号获知引擎属性，信号不会在会话唤醒、面板重启或 disable/enable 后重放；错过信号的面板会退回组件 XML 里的静态 `<symbol>微</symbol>`。因此属性列表（`IBusPropList`）由引擎实例长期持有（`g_object_ref_sink` 使其非浮动，`ibus_engine_register_properties` 只释放浮引用），并在每次 `focus_in` 重新发布一次 `RegisterProperties`，与 ibus-rime 的做法一致；`enable` 不参与属性发布。该属性为 `PROP_TYPE_NORMAL`，同时设置 symbol（中/英）、label（中文/英文）与 tooltip，面板中激活它（`property_activate`）等于切换中英，行为与 ibus-rime 的 `InputMode` 属性一致。
